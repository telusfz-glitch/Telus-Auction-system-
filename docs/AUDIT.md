# Security, code and performance audit — 30 Sep 2026

Scope: the whole repository at the head of `claude/project-start-continue-8mn8ww` (API, web app, database migrations, Keycloak
realm, AWS Terraform). About 6,800 lines of production code were read; every fix below comes with a test that fails without
it, and all suites pass afterwards (API 182, web unit 32, browser end-to-end 13, Terraform plan tests, Checkov).
This is an internal review, not a substitute for the third-party penetration test on the roadmap.

## Architecture and data flow (as reviewed)

```
Browser ──HTTPS──▶ ALB + WAF ──▶ web (Next.js BFF) ──server-to-server──▶ API (NestJS) ──▶ PostgreSQL (RLS)
   │                                   │  session in Redis (encrypted)          │  outbox ──▶ Socket.IO (Redis adapter)
   │                                   └──▶ Keycloak (OIDC, MFA)                └──▶ Stripe, SMTP, S3 Object Lock
   └──WSS (one-time ticket)────────────────────────────────────────────────────▶ API /realtime
```

- **Identity:** Keycloak issues tokens; the web server keeps them (browser holds an opaque session cookie only); the API
  verifies each token (issuer, audience, RS256 only, staff must show `otp`).
- **Authorisation, twice:** API route guards (deny-by-default) and PostgreSQL row-level security on every table, with the
  API connecting as a role that cannot bypass it. Money and state changes go through database functions and triggers.
- **Bids:** customer lock → checks → lot lock → trigger re-checks → outbox row in the same transaction → pushed to rooms.

## Security findings

### S1 (High) — WAF rate limit shared by every customer
**What:** the WAF blocks any address that sends more than 3,000 requests in 5 minutes. But customers never call the API
from their browsers: the web server does, and in AWS all its outbound traffic leaves through the NAT gateways — one or two
addresses for everybody. Token refreshes to Keycloak take the same path.
**Scenario:** a busy auction (a few hundred bidders, each page view making several API calls) passes 3,000 requests in 5
minutes within seconds; the WAF then blocks the NAT address and **every customer gets errors at once**, for minutes. An
attacker who can generate traffic through the web app can trigger the same thing on purpose.
**Fix:** `infra/aws/alb.tf` — the rate rule now ignores our own NAT addresses (`aws_wafv2_ip_set.own_egress`). The API's
per-user limits (step 10) still apply to that traffic. Asserted in `infra/aws/tests/plan.tftest.hcl`.

### S2 (Medium) — the audit trail recorded the wrong address
**What:** for the same reason, every bid and audit entry stored the web server's (in AWS: the NAT's) address.
**Scenario:** investigating a disputed bid or an account takeover, the recorded address is the same for everyone: useless.
**Fix:** the web app forwards the end user's address (the last `X-Forwarded-For` entry, which the load balancer appends)
together with a secret shared only by the web app and the API (`CLIENT_IP_FORWARD_SECRET`, generated by Terraform and
`scripts/gen-secrets.sh`). The API accepts the address only with that secret and only if it is a valid IP, so a customer
calling the API directly cannot choose what is written to the audit log. Tests: `apps/api/test/ops.e2e.spec.ts` (right key,
wrong key, malformed address) and `apps/web/test/lib.test.ts` (header parsing).

### S3 (Low) — readiness check as a lever on the database
**What:** `GET /health/ready` is public and unthrottled (load balancers need it) and used one database connection per call.
**Scenario:** a flood of requests to it occupies the connection pool and slows real users.
**Fix:** one result is shared for 2 seconds: 50 simultaneous calls cost one query (test in `ops.e2e.spec.ts`).

### S4 (Low) — broken connections back in the pool
**What:** if a transaction failed and the following `ROLLBACK` also failed (connection cut mid-transaction), the connection
was returned to the pool and the next request could receive it.
**Fix:** `DbService` now destroys such a connection (`release(error)`).

### S5 (Low) — Excel import size — fixed in the follow-up
An `.xlsx` file is a zip; a crafted 2 MB file could expand to far more in memory while the web server reads it. The
import now reads the archive's directory first (no decompression) and refuses a workbook that declares more than 50 MB
unpacked, more than 200 entries, or ZIP64 — a 200 MB "bomb" packed into ~200 KB is refused before it is opened
(`apps/web/test/lot-import.test.ts`). Sizes in the directory are declared by the file, so this stops ordinary bombs, not
a hand-crafted lying archive; uploads remain limited to auction managers with an authenticator app.

### S6 (Info) — price probing in hidden-price auctions
In auctions that do not show prices, a bid below the minimum is refused with "too low" (without the amount). A bidder can
therefore find the current price by trying amounts; each successful try is a real, binding bid, and bids are limited to 20
per 10 seconds per user. This is inherent to telling bidders their bid is too low. Options, if wanted: record repeated
"too low" attempts in the audit log, or alert on them.

### S7 (Info) — token lifetime after suspension
Unchanged and documented as README gap 6: a suspended login is refused bids immediately (checked in the database), but an
open live-update connection keeps receiving public auction events for up to 5 minutes.

### Checked and found sound
Token verification (algorithm pinning, audience, issuer, MFA claim, mixed-role refusal); deny-by-default guards;
row-level security on every table, including functions that bypass it only after checking the caller; all SQL
parameterised (dynamic column lists come from fixed whitelists); `.strict()` validation on every request body; OIDC login
(PKCE, state, nonce, single-use callback, no open redirects); encrypted server-side sessions with refresh locking;
back-channel logout (signature, audience, event, replay); CSRF (same-origin checks on logout and server actions);
Content-Security-Policy with nonces; socket tickets (single use, 30 s, separate key); Stripe webhooks (signature over the
raw body, amount and currency checked in the database, idempotent); secrets never logged; Keycloak admin actions confined
to customer roles and the caller's company.

## Code audit findings

- **C1 — one pricing rule, two implementations.** The minimum next bid was computed in the bid engine (to refuse) and again
  for the lot table (to display). A change to one would have made the screen show a minimum the server rejects. Now
  `apps/api/src/bids/pricing.ts` (`minNextBid`, `loadBrackets`) is used by both, with unit tests (`test/pricing.spec.ts`).
- **C2 — role groups defined in 8 places.** "Auction managers", "finance", "bidders" and the customer role ranking were
  literal lists in API controllers, the token verifier, the web session and the web UI. They are now defined once in
  `@telus/shared` (`AUCTION_MANAGERS`, `LIMIT_SETTERS`, `SECURITY_ADMINS`, `CUSTOMER_BIDDERS`, `CUSTOMER_ROLE_RANK`).
- **C3 — four identical helpers.** Four services each had a private "run as this user and translate database errors"
  function; it is now `DbService.run`.
- **Not changed, on purpose:** SQL lives in the services rather than a repository layer. At this size it keeps each rule
  next to the query that enforces it and is easy to review; revisit if the services grow much larger. No large refactor
  was made before go-live: the structure is already modular (one module per domain) and every behaviour is covered by tests.

## Performance findings

### P1 (High) — live page refresh multiplied by spectators
**What:** on every push event the auction page re-rendered itself from the server (page render + several API calls +
database queries). In a price-visible auction every accepted bid is pushed to **every** spectator, so load grew with
bids × spectators: 5 bids/s with 1,000 spectators is 5,000 page renders per second.
**Fix:** `apps/web/src/lib/refresh-scheduler.ts` — price broadcasts refresh each browser at most once per ~2 s, spread
over a random 1 s window so browsers do not all arrive together; events about the customer's own position ("you are
leading", "you were outbid") and auction open/close still show within 150 ms. In the same example: at most ~400 renders
per second instead of 5,000, and a busy minute costs each browser ~24 refreshes instead of 300 (tests in
`test/refresh-scheduler.test.ts`; the browser suite still sees live updates).
**Follow-up (done):** in price-visible auctions the pushed price now appears in the "Current bid" cell at once, without
waiting for the refresh (`components/LivePrice.tsx`; it never shows a lower price than it has seen, so an older render
cannot undo a newer push). The minimum next bid still comes only from the server, so the pricing rule stays in one
place. A new browser test covers a full-price auction end to end.

### P2 (Medium) — purchase-limit check inside every bid
Measured on a copy with 200 customers, 50,000 lots and 520,000 bids:

| Query (runs inside the customer's lock on every bid) | Before | After |
|---|---|---|
| Value of lots the customer currently leads | 16.6 ms (reads all 50,000 lots) | **1.9 ms** |

Fix: new index `lot_bid_state_leader_idx` and a join through `lot_bid_state.auction_id` (identical results verified for all
200 customers). Migration `013_performance_indexes.sql`.

### P3 (Low) — other indexes
"My highest bid" on a lot with 20,000 bids: 9.4 ms → 5.7 ms (index-only scan, `bids_lot_customer_idx`); a customer's
invoices and a company's logins now have indexes too. On a live database, create large indexes with `CONCURRENTLY` first
(the migration explains how).

### P4 (Medium) — lot table for large auctions — fixed in the follow-up
Measured with 1,000 lots, 50 bidders and 20,000 bids: the customer lot table (`/auctions/:id/my-positions`, loaded on
every page view and refresh) took ~90 ms warm (~370 ms cold), 70 ms of it in two small functions called once per lot.
One function for the whole auction (`auction_lot_positions`, migration 014, same visibility rules) brings it to
**~6 ms**. Results were compared lot by lot for a leading customer, an outbid one and an uninvited one, in both
price-visible and hidden auctions (identical), and a new test pins the rules (`bids.spec.ts`: it fails if the function
ever returns the price in a hidden auction).
